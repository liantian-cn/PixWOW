# 项目开发思路

## 支持的环境与取舍

五个应用各自维护一套配置、一个循环和独立插件；不合并代码或增加循环配置档。专精策略、技能数值和目标顺序以对应项目的 `.context/rotation.md` 及用户决定为准。

按一般游戏进程设计。例如普通五人副本小队通常只有一名坦克和一名治疗，不为多个坦克、多个治疗等罕见组合主动扩展选择算法。兽王误导先取第一位存活在线坦克，再检查其射程。审查应区分已支持场景中的错误与用户未要求支持的特殊环境，不能把后者直接列为必须修复的问题。

用户确认的设计约定具有明确范围；只有代码偏离约定、支持环境变化或出现新的具体故障证据时，才重新讨论。既有实现本身不证明满足规范，也不能用改文档掩盖代码偏离用户需求。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| Lua | 采集状态、编码和显示；允许原生曲线、射程计数、配置归一化及显示生命周期处理 |
| capture.py | 截图、定位及采样帧发布 |
| matrix.py | 像素几何、颜色／条长／图标等基础解析，不放专精业务量程 |
| context.py | 为像素数据提供有语义的状态属性及必要派生状态 |
| rotation.py | 业务数值、资源换算、门控、治疗评分、技能优先级及目标选择 |
| action.py / keyboard.py | 顺序调度动作／发送按键 |

未来可能随主流版本变化的业务数值放在 rotation，不下沉到 Matrix。新建类似资源接口时，Context 优先提供原始比例，由 rotation 按业务上限换算。例如血 DK 当前上限为 125 点且战斗中不变化：Context 返回 `power_runic_power_ratio`，rotation 计算 `power_runic_power = ctx.power_runic_power_ratio * 125`。此要求不授权重构其他已经稳定的资源接口。

Rotation 不直接截图、发键、阻塞休眠或修改 UI；保留首个命中即返回及 Cast／Use／Idle／Sleep 的现有语义。新增动作必须有对应键位和宏，动态治疗动作要核对实际单位。

## 文档分工

- 本目录保存五项目共用的设计与经验；各应用 `.context` 保存该专精当前的布局、键位及循环规则。
- [代码质量控制](code-quality.md)保存业务注释、刷新和验证要求；[WoW API 与解析约定](wow-api-notes.md)保存 API 检查方法及已确认的项目边界。
- Skill 描述执行流程，并按需引用这些文档；同一条规则只维护一个正文，不将可变技能数值复制进 skill。
- 修改范围以用户需求为准，复用现有模式和依赖，不附带重构、通用框架或新的历史审计报告。提交与文件备份遵守[根 AGENTS.md](../AGENTS.md)。
